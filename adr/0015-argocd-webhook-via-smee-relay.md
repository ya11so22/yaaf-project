# ADR-0015: Trigger Argo CD from GitHub with a webhook, relayed by smee.io

**Status:** accepted (extends [ADR-0013](0013-gitops-with-argo-cd-on-long-lived-aws.md))
**Date:** 2026-09-21

## Context

Argo CD polls git every 120 seconds plus up to 60 seconds of jitter in the chart used here, so a merged
image bump reached the cluster up to three minutes later. Argo's intended answer is a GitHub webhook to
its `/api/webhook` endpoint. The obstacle is reachability: Argo runs in a cluster on the owner's machine
behind NAT, and GitHub cannot call it.

Options compared (current documentation, September 2026):

| Option | Cost, account | Stable URL | Exposes Argo publicly | Main limits |
|---|---|---|---|---|
| Poll faster | free | n/a | no | not event-driven; Argo keeps polling anyway |
| smee.io relay | free, no account | yes (channel ID) | no (outbound connection only) | "for development, not production"; channels are unauthenticated; **cannot preserve the webhook signature** (below) |
| ngrok free | free, account | one static dev domain | yes | 1 GB and 20,000 requests a month; interstitial page |
| Cloudflare quick tunnel | free, no account | no, random per start | yes | no SLA; dev and test only |
| Cloudflare named tunnel | needs a domain on Cloudflare | yes | yes | not free without a domain |
| Tailscale Funnel | free, account and tailnet | yes | yes | ports 443, 8443, 10000 only; unpublished bandwidth limits |
| Self-hosted Actions runner | free | n/a | n/a | rejected: on a public repository it runs pull-request code on the owner's machine |

Floci also emulates the AWS-native shape of this (API Gateway, Lambda, EventBridge, SQS), but it does
not remove the reachability problem: Floci's endpoints are `localhost` too.

**The signature limit.** GitHub signs each webhook (`X-Hub-Signature-256`) over the exact bytes of the
body, and Argo can verify it with a shared secret. smee.io parses the body on its server, and the
smee client forwards `JSON.stringify(data.body)`: a re-serialisation, not the original bytes. GitHub
escapes characters such as `<` and `>` as `<` and `>`, and this repository's commit messages
contain `<noreply@anthropic.com>`, so the bytes differ and no signature can verify. This was not
known when smee was first proposed, and an earlier statement that Argo would reject forged events
through a shared secret was wrong for this route.

## Decision

1. **Route:** GitHub push webhook → a smee.io channel → the smee client running in the cluster →
   `http://argocd-server.argocd.svc.cluster.local/api/webhook`. The cluster only makes an outbound
   connection; Argo stays private. Argo's normal polling stays on.
2. **No webhook secret** is configured, since it cannot verify through smee. The webhook is treated
   as a poke only: on receiving one, Argo refreshes and reads the state from git itself, so a forged
   event cannot inject anything; at worst it triggers a refresh. Argo ignores events for repositories
   it does not manage. The channel ID, 24 random hex characters generated by OpenTofu and kept out
   of git, is the only thing limiting who can post to it.
3. **The relay client** runs as a Deployment created by OpenTofu in the `floci-cluster` root (it needs
   the channel URL, which stays out of git): a Node 24 image pinned by digest, `smee-client` pinned,
   non-root, read-only root filesystem, no added capabilities.
4. **The GitHub webhook** is created or updated by `scripts/dev-up.ps1` through the GitHub API, using
   the owner's `gh` login, pointing at the channel. A failure there is a warning, not a failure.
5. **The AWS mirror is deferred to the real-AWS milestone.** There, API Gateway (or a load balancer)
   in front of Argo's webhook is publicly reachable, needs no relay, and receives the raw body, so
   signature verification works and the shared secret is set. Floci can rehearse it (API Gateway,
   Lambda, Secrets Manager). It is recorded as a real-AWS item, not built now.

## Consequences / trade-offs accepted

- The route is weaker than a signed webhook: anyone who learns the channel ID can read the (public)
  push-event payloads and post events that make Argo refresh. This is acceptable for a disposable dev
  environment, and is not acceptable for anything that matters. The real-AWS route restores
  verification.
- smee.io is a community service with no availability guarantee. If it is down, Argo falls back to
  its own polling, so the effect is the old delay, not a failure.
- The relay pod installs `smee-client` from npm when it starts, pinned by version.
- If signed delivery is wanted locally, a tunnel that forwards raw bytes (ngrok, Cloudflare, Tailscale
  Funnel) is the alternative, at the cost of publicly exposing Argo and, for most of them, an account.
