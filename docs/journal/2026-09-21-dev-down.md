# 2026-09-21: A safe shutdown for the local AWS

**Phase:** Phase 1, operating the long-lived AWS
**Related ADRs:** [ADR-0014](../../adr/0014-operating-the-long-lived-aws.md), decision 7

## What happened

The owner wanted to close Docker and use the laptop for other things, and asked how to return everything
safely and quickly. Checking the machine showed nothing is removed by quitting Docker Desktop: the state is in
three Docker volumes (Floci's data, the cluster's datastore, the registry's images) and two OpenTofu state
files that exist only on disk (gitignored, so not on GitHub). Losing the state files while the Floci volume
survives would make OpenTofu try to create resources that already exist. So the return path is
`dev-up.ps1` (already idempotent), and the missing piece was its counterpart:

`scripts/dev-down.ps1` backs up the two state files (timestamped, newest 5 kept), stops Floci gracefully, stops
anything Floci started (found by its `floci=true` label), and with `-QuitDocker` quits Docker Desktop. It removes
nothing. `-DryRun` does the backup but stops nothing.

## Findings

- My first test passed a mangled path (the shell expanded `$env:TEMP` before PowerShell saw it), the copy failed,
  and the script still printed "Backed up 2 state file(s)". A backup step that reports success after failing is
  the dangerous kind of bug. It now catches errors, checks that the copied file exists, and reports the failure.
- Windows PowerShell 5.1 and PowerShell 7 both pass the same tests.

## Verification

On both shells: a dry run backed up both state files and the backups were byte-identical to the originals;
two runs with `-KeepBackups 1` left one folder; an invalid backup path was reported as a failure with nothing
deleted; no dry run stopped any container. Not run: the real stop and `-QuitDocker`, since that would take down
the environment being used; the first real use is the owner's.
